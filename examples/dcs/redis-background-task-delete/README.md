# Delete a DCS Background Task

This example provides best practice code for using Terraform to delete a background task of a DCS
(Distributed Cache Service) instance in HuaweiCloud. It operates on a **pre-existing** DCS instance
and background task — no infrastructure is created by this configuration.

## Prerequisites

* A HuaweiCloud account with DCS permissions
* A **pre-existing** DCS instance with at least one background task
* The ID of the background task to be deleted (obtainable via DCS console or API)
* The ID of the DCS instance that owns the background task
* Terraform installed
* HuaweiCloud access key and secret key (AK/SK)

## Variable Introduction

The following variables need to be configured:

### Authentication Variables

* `region_name` - The region where the DCS instance is located
* `access_key` - The access key of the IAM user
* `secret_key` - The secret key of the IAM user

### Resource Variables

* `dcs_instance_id` - The ID of the DCS instance that owns the background task (default: `""`)
* `background_task_id` - The ID of the background task to delete (default: `""`)

## Usage

* Copy this example script to your `main.tf`.

* Create a `terraform.tfvars` file and fill in the required variables:

  ```hcl
  dcs_instance_id    = "your_dcs_instance_id"
  background_task_id = "your_background_task_id"
  ```

* Initialize Terraform:

  ```bash
  $ terraform init
  ```

* Review the Terraform plan:

  ```bash
  $ terraform plan
  ```

* Apply the configuration:

  ```bash
  $ terraform apply
  ```

## Note

### Delete-Action Resource

This resource is a **delete-action** resource. Its behavior differs fundamentally from standard
Terraform resources:

* **Create triggers deletion**: The `create` operation sends a `DELETE` request to the DCS API
  (`DELETE /v2/{project_id}/instances/{instance_id}/tasks/{task_id}`) to remove the specified
  background task. The resource is then tracked in Terraform state with its ID set to the `task_id`.
* **Read is a no-op**: The `read` operation does not query the API. Terraform will not detect
  configuration drift for this resource.
* **Update is a no-op**: The `update` operation does nothing. Both `instance_id` and `task_id` are
  non-updatable — changing either will trigger resource replacement (ForceNew).
* **Delete is a no-op**: Running `terraform destroy` only removes the resource from Terraform state.
  The deleted background task is not restored. A warning message is displayed during destruction.
* **No import support**: This resource cannot be imported into Terraform state.

### Why Not Use a Data Source for task_id

Do **not** use the `huaweicloud_dcs_background_tasks` data source to dynamically feed `task_id`
into this resource. The reasons are:

* After `terraform apply` deletes the task, the data source returns a **different** `tasks[0].id` on
  the next read (the original task is gone).
* During `terraform destroy`, Terraform re-reads the data source, detects that `task_id` has changed,
  and the `FlexibleForceNew` CustomizeDiff blocks the operation with:
  `task_id can't be updated`.
* This makes `terraform destroy` permanently fail.

Always use a **static variable** for `task_id` so it remains stable across plan/apply/destroy cycles.

### Immutable Parameters

* `instance_id` — Non-updatable. Changing this value triggers ForceNew (resource replacement).
* `task_id` — ForceNew. Changing this value triggers resource replacement.

### Background Task ID

* The `background_task_id` must correspond to an actual background task on the specified DCS instance.
* Background tasks are generated by the system during operations such as instance creation, scaling,
  configuration changes, backup, restoration, etc.
* You can obtain the background task ID through the DCS console or the
  `GET /v2/{project_id}/instances/{instance_id}/tasks` API.
* Once a background task is deleted, it cannot be recovered.

### Resource ID

* The Terraform resource ID (`id`) is the `task_id` itself, not a UUID or composite key.

### Security

* Keep your AK/SK credentials secure and never commit them to version control.
* Use environment variables or a secrets manager for sensitive values in production environments.
